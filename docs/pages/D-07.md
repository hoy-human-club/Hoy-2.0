# D-07 — API keys

**Route** `/#/dev/api-keys` · **Roles** super_admin, developer, admin · **Surface** dev · **Spec** `spec.code === 'D-07'` (see `/#/dev/specs`)

## Purpose
The keys HoyOS issues to developers to call its API: create (with environment, scopes and an optional expiry), see once, rotate with a 24-hour grace period and revoke. Only a prefix and the SHA-256 hash are stored; the server will do the verification.

## Logic and integrations
- Format hoy_<live|test>_<24 base62> from crypto.getRandomValues (rejection-sampled); stored: prefix (13 chars) + SHA-256 hex via crypto.subtle. The raw key lives only in current-command memory and then component state until the drawer closes; receipts contain metadata only.
- Rotate inserts a new key with replaces_id = old id and the old key’s lifetime (same duration from now; never-expiring stays never), and sets the old key’s expires_at to now + 24 h (unless it already expires sooner). Revoke sets revoked_at; rows are never deleted.
- Status: revoked (revoked_at) · expired (expires_at past) · expiring (within 7 days) · active.
- api_keys.write (super_admin, developer) gates create / rotate / revoke; admin reads the list (api_keys.read). Every write is audited: api_key.create / api_key.rotate / api_key.revoke with the prefix, never the key.
- Verification is a server concern (D-0018): hash the bearer token, match key_hash, check environment, scopes, expiry and revocation, stamp last_used_at. The clearly labeled symbolic fictional request console remains disconnected from HTTP and verification.
- Integrations: HoyOS HTTP API (designed, not built)

## Real vs mock
- Browser-only fiction: CSPRNG generation and Web Crypto hashing are real browser operations, but the resulting mock strings are not accepted by any service; rows, grace, revocation and audit are local simulation state.
- Mock / pending: nothing verifies a key yet — verification, `last_used_at` stamping and the HTTP API are the server’s job (D-0018).
- Actions (WebMCP): `dev.apiKeys.create`, `dev.apiKeys.rotate`, `dev.apiKeys.revoke` — they answer with the prefix, never the raw key.

## Batch20: fictional command atomicity

Create, rotate and revoke now stage key writes and their audit together. Local write or persistence failures preserve the previous state and permit retry; immediate identical commands share one flight. Stable mock receipts contain metadata only. A committed command with a lost acknowledgement returns metadata on retry and never recovers or redisplays the raw value. Cancellation clears current-command material; it cannot undo a command already committed. Actor/role/tenant changes and changed target snapshots prevent pending staged writes.

Validation rejects unknown/empty scopes, invalid environments, empty names and malformed/nonfinite/negative expiry durations. Existing UI choices0/30/90/365, default90, never0, and numeric fractional action durations remain. A malformed local stored expiry is diagnostic and blocks rotation; revocation remains available. Existing roles/scopes, purchased terms and server disconnection are unchanged. See [batch20](../frontend-completion/batch-20.md) for tests and limits.
