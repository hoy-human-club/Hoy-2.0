# Batch 7 — fictional transfer receipt request and review

Requirements: PG-02, PG-04, PG-05. Original phase remains **MVP Oct 30**. Source criteria and acceptance statuses remain unchanged. Frontend evidence is separate from owner/backend acceptance. No row is fully accepted by this batch.

Baseline: remote main `b73c13a` (PR59), v0.25.0. Repository recovery only; no prior denied environment accessed. No AGENTS.md exists; CLAUDE.md engineering contract applies. Checkout `/app/checkout/:id` (C-04) now offers a **demo transfer** with PNG/JPG receipt selection, byte-signature/type/extension/2MB validation, browser image decoding and dimension ceiling, visible preview/removal, and an unmistakably fictional generated image. No bank details/QR are invented. The screen explicitly forbids real transfers and labels the image copy as local to this browser, with no server upload or cross-device retention.

Submission stages one pending fictional payment and its receipt snapshot; it creates no active booking, entitlement or capacity hold. Failure rolls back both, retry uses the same request key, and concurrent identical submissions deduplicate. The original product name, quantity, amount and validity are retained in the request. The provisional validity reflects the existing catalog's current frontend values; it does not replace historical purchased terms.

`/staff/transfers` and `/staff/transfers?receipt=<id>` (S-09) give front desk and Administration a local pending list with customer, product, amount, receipt and received time. Status filters expose approved/rejected history. Loading, empty and read-error/retry states are implemented. The confirmation deadline is explicitly unresolved instead of an invented countdown (PG-03/PC-01 requires Jas's decision). No hold is implied. Review requires amount, reason and explicit comparison with a clearly marked **fictional** bank notification; Bancolombia remains disconnected. The mock approval requires an exact amount; under/overpayment settlement remains unresolved and such requests can be rejected with a reason. This is a conservative prototype constraint, not approved commercial policy.

Approval atomically changes the fictional payment, activates the original request quantity/validity and optionally books the requested class after rechecking session/duplicate/capacity/entitlement restrictions. An unavailable class, occupied selected mat, injected/provider/storage failure leaves the request pending and all writes unchanged. Trial eligibility is rechecked at approval against existing approved trial payments/bookings, so two previously pending trial requests cannot both activate. The rejected approval retains the pending request unchanged with a specific message. Repeated identical decisions have no duplicate effect; opposing decisions fail. Rejection records the reason and amount without granting classes or booking. No notifications are sent. This is client demo role gating, **not authenticated server authorization**. The route does not expand Finance/coordinator/customer access.
